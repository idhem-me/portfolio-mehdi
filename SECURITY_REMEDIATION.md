## Choix de dépendances explicites

- `vendor/deepmerge` conserve l’API et le code MIT de deepmerge 4.3.1, avec rejet récursif de `__proto__`, `constructor` et `prototype` **dans la cible et dans la source**. L’avis n’avait pas de version amont corrigée disponible. Le patch est lisible, documenté et testé ; le numéro local ne doit pas être interprété comme une publication officielle. Remplacer ce patch lorsqu’une correction amont compatible sera disponible.
- `vendor/minimatch-compat` conserve l’export CommonJS callable attendu par certains plugins ESLint, mais délègue toutes les recherches au moteur amont 11.0.3 verrouillé via un alias npm. Aucune copie du moteur vulnérable v3 ne subsiste. Une substitution directe par v11 casserait l’API de ces plugins.
- `.npmrc` définit `install-links=true` afin que les paquets locaux soient empaquetés correctement, et non référencés par des liens dépendant de l’emplacement de node_modules. Aucune référence au dossier temporaire de validation dans le lockfile.
- Les scripts d’installation tiers n’ont pas été exécutés pendant l’installation propre de validation. Les binaires natifs fournis par les dépendances optionnelles fonctionnent dans les tests et dans le build.

## Mise en service, dans cet ordre

1. **Sauvegarder la base et appliquer la migration** `supabase/migrations/20261031155314_security_hardening.sql` après les migrations existantes. Elle ajoute quatre tables privées avec RLS, des RPC réservées à service_role, l’association visiteur des batches, et ferme les RPC d’import local. Elle ne supprime pas de sauvegarde de jeu canonique ni de contenu cadeau.
2. **Configurer côté serveur** `SECURITY_HASH_KEY` : valeur aléatoire de 32 caractères minimum, identique pour toutes les instances d’un même environnement. Générer par exemple avec `openssl rand -hex 32`, sans copier le résultat dans Git ou dans le rapport. Utiliser des valeurs distinctes pour production et previews.
3. **Configurer `DASHBOARD_PASSWORD`** : mot de passe long, unique, au moins 12 caractères, différent de l’ancien exemple. Aucun remplacement automatique du mot de passe local n’a été effectué. Les anciennes sessions administrateur déterministes seront toutes invalidées.
4. Vérifier les variables serveur Supabase et `CRON_SECRET`. Le cron existant purge maintenant aussi les sessions de sécurité, quotas, capacités et leases expirés.
5. Déployer le code avec son lockfile et le répertoire `vendor`. Ne pas publier le code avant l’application de la migration si l’on veut éviter une interruption des fonctions dépendantes : le refus par défaut est intentionnel lorsque le stockage de sécurité manque ou tombe en panne.
6. Vérifier sur le domaine réel : login administrateur, back-office, logout puis rejeu du cookie refusé ; acceptation puis retrait du consentement ; nouvelle capacité visiteur ; réservation/annulation cadeau ; upload avatar et couverture ; quotas multi-instances ; cron et logs sans secrets.
7. Exécuter Security Advisor Supabase sur la base déployée, contrôler WAF/quotas de création de comptes invités, restrictions Web3Forms, Deployment Protection, budgets et alertes de facturation. Ces réglages plateforme ne sont pas activés par un changement de code du dépôt.

**Configuration locale observée sans exposer ses valeurs :** Supabase est configuré ; `SECURITY_HASH_KEY` manque et le mot de passe administrateur actuel ne satisfait pas le nouveau minimum. Les fonctions protégées restent donc fermées jusqu’à configuration et migration. En développement uniquement, une clé HMAC éphémère de processus permet les tests manuels ; un redémarrage invalide alors les capacités. Ce fallback n’existe pas en production/Vercel.

Les anciens UUID visiteurs ne sont jamais convertis en capacité privée sur simple présentation de l’identifiant : ce serait réintroduire SEC-007. Leurs données restent soumises à la rétention existante de 90 jours. Les sauvegardes locales Cartes restent sur l’appareil, mais ne peuvent plus être promues vers le serveur sans preuve de provenance.

## Limites assumées

La CSP globale conserve `script-src 'unsafe-inline'` pour les scripts de bootstrap de Next Cache Components ; elle bloque le framing, les objets actifs, les handlers inline et limite les domaines, mais n’est pas une CSP stricte à nonces. Le passage à une CSP à nonces demande de revoir la stratégie de rendu/cache et de retester les intégrations ; il n’est pas présenté comme acquis par cette correction.

Les budgets PostgreSQL sont un contrôle d’abus applicatif partagé. Ils ne remplacent pas le WAF ni les limites anti-DDoS avant invocation. L’adresse réseau n’est utilisée que depuis le header protégé par Vercel et pseudonymisée par HMAC ; hors Vercel, les demandes partagent volontairement un quota conservateur plutôt que de faire confiance à un header arbitraire.

Les contrôles des dashboards et les parcours positifs sur les vraies intégrations restent à effectuer lors de la mise en service. Les tests de handlers utilisent un transport Supabase simulé, complété par les tests SQL ; ils ne sont pas présentés comme un test de production.
